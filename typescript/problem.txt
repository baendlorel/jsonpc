## A. 日期字面量

**A1. 只接受一种形态**
当前只认 `YYYY-MM-DDTHH:mm:ss.sssZ`（3 位毫秒 + `Z`），拒绝：
- `2024-01-02T03:04:05.678000Z`（Python `isoformat()` 默认输出）
- `2024-01-02T03:04:05.678+08:00`（带偏移）

建议：明确规范只支持 `toISOString()` 形态；或放宽为 `.{1,9}` 且允许偏移。
你的决定：
还是只留3位吧，因为js里只有3位，其他语言有6位9位，多了也无意义

**回应**：采纳。规范固定为 `Date#toISOString()` 的精确形态 ——
`YYYY-MM-DDTHH:mm:ss.sssZ`，恰好 3 位毫秒、必须带 `Z`、不接受时区偏移。
其他语言实现者需自行把 6/9 位时间截断/补齐到毫秒。

**A2. 扩展年份写出去读不回来**
`new Date('+010000-01-01T00:00:00.000Z').toISOString()` 输出 `+010000-…`，
`tagExtensions` 已加 `ISO_DATE_EXT` 识别（`[+-]\d{6}`）。需确认是否作为正式语法。
你的决定：
是的，正式语法。

**回应**：采纳，已作为正式语法写入规范。规则：年份为 4 位时无符号；
为 6 位时必须带 `+`/`-`（`+010000`、`-000001`）。
注意 `-000000` 在 JS 中解析为 `Invalid Date`，会被 A3 的校验拒绝。

**A3. 非法日期不报错**
- `2024-13-01T…Z`：构造/`get()` 通过，得到 `Invalid Date`；到 `toObject()` 才抛 `Invalid time value`。
- `2024-02-31T…Z`：静默滚动成 `2024-03-02T…Z`（JS `Date` 行为），其他语言会拒绝。

建议：解析时统一校验，非法日期在构造阶段就抛错。
你的决定：
非法日期要报错。非法值解析的时候肯定要报错的。

**回应**：采纳并已实现。校验方式采用「规范形式往返比较」：

```ts
const d = new Date(raw);
if (Number.isNaN(d.getTime()) || d.toISOString() !== raw) throw new SyntaxError(...);
```

这条判据同时覆盖三种情况：`2024-13-01`（Invalid）、`2024-02-31`（被滚动，
回写后不等于原文）、扩展年份（能原样往返）。所有语言都有等价手段
（先按规范格式解析，再按规范格式回写比对）。

## B. 数组元素注释（自相矛盾）

`stringify()` 会在数组元素前输出注释（serializer.ts），但解析端只允许注释位于属性名上方。

```ts
const j = parse('{"arr":[1,2]}');
j.set('arr.0', { value: 1, comments: ['c'] });
parse(j.stringify()); // THROW: Comments are only allowed directly above property names
```

建议二选一：
1. 解析端允许数组元素上方的注释（改 `interpret-name.ts` 与 README）；
2. `stringify()` 不输出数组元素注释（`set` 时忽略或另存）。

你的决定：
这里需要详细研究如何给array的每个item上一个comment。这个很麻烦。稍后再说，你在合适的位置加todo

**回应**：暂不处理。已在 `src/core/serializer.ts` 的数组元素注释输出处
和 `src/walkers/interpret-name.ts` 的校验处加了 TODO，指向本条。
在敲定方案前，规范里对数组元素注释保持「不支持」的描述。

## C. BigInt

**C1. `n` 后缀语义**
`n` 在 Python/Ruby 是虚数单位。是否接受这一歧义？
你的决定：
我不支持ruby。另外python一定有大整数、大数库，这里需要引入大数库或者语言自带的大数表达来参与其中
各个语言肯定都有各种方法，原生或第三方库支持大数。这里选用js里的n表示，纯粹是因为json本身脱胎于js

**回应**：采纳。`n` 定义为「大整数后缀」，与 JS BigInt 对齐；不涉及复数语义。
规范声明：实现方应使用语言原生任意精度整数（Python `int`、Java `BigInteger`、
Rust `num-bigint` 等），超出实现能力时拒绝解析，不得静默降级为浮点。

**C2. 字面量规范化**
解析会静默规范化：`007n` → `7n`，`-0n` → `0n`。是否在规范中固定此行为？
你的决定：
无所谓，BigInt构造函数允许就允许。

**回应**：采纳。规范不额外限制前导零，按宿主 `BigInt` 构造函数的行为处理；
这属于「实现允许即可」，不写死为必须保留原文。

**C3. 与标准 JSON 的边界**
超过 2^53 的整数不加 `n` 时，JS 丢精度（`9007199254740993` → `…992`）。是否在 README 强制提示？
你的决定：
加提示即可，加不加n是用户自己的决定。

**回应**：采纳，在 README 的 Extended Values 里加提示：超过 ±2^53 的整数
若需要精确表示，请自行加 `n`；不加则按宿主浮点数精度处理。

## D. NaN

**D1. 比较语义**
`NaN !== NaN` 是 JS 规则，Python/Rust/Java/C#/Go 同样；但若用「值相等」做 diff/去重，各实现需特殊处理。
建议：规范声明比较语义由宿主语言决定。
你的决定：
由宿主决定

**回应**：采纳。规范只规定 `NaN` 是一个合法值，不规定比较语义。

**D2. 是否支持 `Infinity` / `-Infinity`**
当前不支持。Python `json.dump` 默认会输出 `Infinity`/`NaN`。
建议：保持不支持，README 明确说明是有意选择。
你的决定：
加入支持，允许。可以新增INF_TAG常量来实现，正则表达式为允许正负号的Infinity。

**回应**：采纳并已实现。字面量文法：`Infinity` | `+Infinity` | `-Infinity`，
不区分大小写以外的写法（`inf`、`INF` 不接受）。
新增 `INF_TAG`，`untagExtensions` 按带符号文本还原为 `Infinity` / `-Infinity`；
`stringify` 对非有限数输出对应字面量。

## E. 标签字符串冲突（实现细节）

U+E000 前缀导致合法字符串被误还原：

| 输入字符串 | 实际得到 |
|---|---|
| `"/xccle*8&NaN"` | `NaN` |
| `"/xccle*8&Date2024-01-02T03:04:05.678Z"` | `Date` 实例 |
| `"/xccle*8&BigInt42n"` | `42n` |

`stringify` 也不会转义这些字符串。
建议：把标签机制定位为内部实现细节（不写进规范）；若要修，需在 `stringify` 时转义 U+E000。
你的决定：
这里我确实没有什么很好的办法，这是用魔法字符串实现的标记。几乎不可能重复。

**回应**：同意接受这一残余风险。规范明确：标签串是实现细节，**不属于语法**，
其他语言实现不必兼容；它们直接用自己的解析器产出真值即可。

## F. 标准 JSON 的跨语言差异（是否纳入规范）

| 场景 | 当前 JS 行为 | 其他语言 |

| 孤立代理项 | 接受并原样输出 | 各语言不一 |
